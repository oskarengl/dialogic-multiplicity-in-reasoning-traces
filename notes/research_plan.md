# Research Plan

## Question

Reasoning models like DeepSeek-R1 produce a long "thinking" trace before they answer. Does that
trace behave like one mind talking to itself, a monologue, or like several distinct voices going
back and forth, a dialogue? This project answers that with measurable text features, not
speculation.

## Data

There is no ground truth for the reasoning traces themselves, so we compare them against four
sets where we do know the answer.

- **Human monologue**: people thinking out loud alone while solving a puzzle. Collected, an
  existing think-aloud corpus.
- **Human dialogue**: groups of people discussing a puzzle together. Collected, an existing
  corpus (DeliData).
- **AI monologue**: one language model, prompted to reason step by step, alone. Generated by us.
- **AI dialogue**: four independent copies of one language model, debating a puzzle with each
  other. Generated by us.
- **AI reasoning traces**: the actual target, the native "thinking" text a reasoning model
  produces on its own. Generated by us.

Human monologue and human dialogue should read as single voice and multiple voices respectively.
AI monologue and AI dialogue should too, by construction. A method only gets to make a call on the
reasoning traces once it gets all four of these right. The five datasets live under
`data/00_core-2x2`, one folder each.

### Task

The methods we use react to what a text is about, not only to how many voices wrote it. If two
texts differ in both topic and structure, we can't tell which one caused a detected difference.
So AI monologue, AI dialogue, and the reasoning traces all use the same task: Game of 24, a small
puzzle where you combine four given numbers to make 24. Human monologue uses it too, which gives
us a same-task check: if a method correctly reads human monologue as single-voice, we know it
isn't just reacting to the puzzle itself.

Human dialogue is the exception. It comes from DeliData, built around a different task, the Wason
card-selection problem. We keep it anyway because its only job is to confirm a method can detect
real human dialogue structure at all; it doesn't need to match the puzzle used elsewhere.

That leaves one honest gap: comparing human monologue to human dialogue always mixes "different
number of voices" with "different task." We don't try to fix that. The comparison that actually
carries the argument is the AI-only one, monologue vs. dialogue vs. reasoning traces, all on the
same task.

### How the generated datasets were made

**AI monologue** is one call to a language model, prompted to solve a Game of 24 puzzle by
reasoning through it step by step.

**AI reasoning traces** are one call to a reasoning model, using its native thinking mode on the
same puzzles. No special prompting for structure; whatever it produces on its own is what we
study.

**AI dialogue** took more care, since a "debate" has to be genuinely multi-voice and not just one
model performing multiple voices. Four separate calls to the same language model take turns
writing the debate, one call per turn. Each call only sees the shared transcript written so far,
nothing from the other calls directly, so the four voices don't share memory beyond what's on the
page. Each has a fixed role (creative problem solver, critical analyst, mathematical validator,
alternative seeker) and a letter, A through D. Turn order is random. A debate ends after 40 turns,
or earlier once everyone has spoken and the conversation looks finished or starts repeating
itself.

We use four copies of one model rather than four different models on purpose, because the
reasoning traces we're studying also come from a single model. If a method can't find multiple
voices in a same-model debate, that says something about the method, not about whether debate
structure exists. We also never ask one model to write a whole four-person script in a single
response; that would just be one voice pretending to be many, the exact thing we're trying to
find out about the reasoning traces, so it can't double as proof that many voices look different
from one.

Build details that changed along the way, and exact model names, are tracked in `STATUS.md`, not
here.

## Methods

This is the core of the project: three independent ways of checking for monologue/dialogue
structure, so no single method has to carry the whole conclusion.

### 1. Style-change detection

**Source:** the PAN Style Change Detection shared task, using Nath's 2019 winning method.
PAN's task was originally built to catch undisclosed multi-author documents, for example spotting
ghostwritten sections in an essay or forum posts stitched together from different contributors.

**How it works:** the text is split into windows (roughly paragraph-sized). Each window's most
frequent 50 words form a style fingerprint, since function-word usage tends to be a stable
personal habit rather than something tied to topic. Windows are then clustered by how similar
their fingerprints are: windows that look stylistically alike get grouped into the same cluster.
The number of clusters found is the predicted number of authors. More than one cluster means the
method calls the text multi-author.

### 2. Sentence-level style-change detection

**Source:** the PAN 2025 Sequential Sentence Pair Classifier (Schmidt et al., 2025), a newer
entry in the same PAN task family. Where the 2019 method only says how many authors a whole
document has, the 2025 task asks for the exact sentence where the author changes, since a real
multi-author document may switch back and forth many times, not just once.

**How it works:** every sentence gets encoded by a pretrained style-embedding model, then the
sequence of sentence embeddings is passed through a BiLSTM so each sentence's representation is
aware of its neighbors. A classifier then looks at each pair of adjacent sentences and estimates
the probability they were written by different people. Averaging that probability across the
whole text gives a single-document verdict: high average probability means frequent style
switching, consistent with multiple voices.

### 3. Dialogue-act tagging

**Source:** the Conversation Analysis Modelling Schema, CAMS (Duran & Battle, 2018), grounded in
Schegloff & Sacks' 1973 work on adjacency pairs. CAMS was built to label what function each
utterance serves in a conversation (a question, an answer, an agreement, a greeting, and so on),
originally so dialogue systems could be trained and evaluated on conversational structure
independent of topic. Adjacency-pair theory describes how certain utterance types come in fixed
response pairs, a question is normally followed by an answer, a suggestion by an acceptance or a
decline, and so on. That pattern is a hallmark of genuine back-and-forth.

**How it works:** every sentence in a trace is labeled with one of 27 CAMS tags describing its
conversational function. We then count how often labels form real adjacency pairs across the
sequence. A text with many question-answer or suggestion-response pairs looks like a dialogue. A
text that is mostly one label after another, "inform, inform, inform," looks like one person
working through a problem alone.

Exact settings and citations for all three methods are in `classification_methods_sources.md` and
the matching `methods` folder.

## Keeping ourselves honest

Every method is fixed and written down before it runs on the real data. If a method doesn't work
on the four known datasets, we don't quietly retune it until it does. Anything we're forced to
change afterward gets written down with a reason, in `STATUS.md`, not edited into this plan.

## Steps

1. Run all three methods on the four known datasets. A method moves on only if it correctly tells
   monologue from dialogue on all four.
2. Run whichever methods passed on the AI reasoning traces.
3. Compare. If the reasoning traces read like the AI monologue, that's evidence for monologue. If
   they read like the AI dialogue, that's evidence for dialogue. If they land in between, we
   report that honestly instead of forcing a label.
